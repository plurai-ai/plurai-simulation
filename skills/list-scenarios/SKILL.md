# List Scenarios

You are the LOCAL Claude Code agent. The customer wants to see what
scenario sets are stored on the Plurai backend — either
the catalog (every set this backend knows about) or the per-scenario
detail for one set.

```
┌── customer's machine (you) ──────────────────────────────────┐
│  Inspection-only. No new generation; no scenarios fetched.    │
│                                                                │
│  Two modes:                                                    │
│    catalog : MCP list_artifacts(kind='scenarios')          │
│              → table of all sets                               │
│    detail  : MCP get_artifact_meta(set_id) → per-scenario     │
│              summary (complexity, subtlety, target_flows, …)  │
└──────────────────────────────────────────────────────────────┘
```

## Preconditions

- `plurai` MCP server reachable (the backend is the configured one, the one the saved Plurai login names; a remote backend requires that login).
- Backend has `scenario_storage_root` configured (same precondition as
  `/generate-scenarios`).

## The flow

### Mode A — catalog (no args)

When invoked without `scenario_set_id`, call `list_artifacts(kind='scenarios')` and
render a table. The tool returns a **list of Job envelopes** (newest first);
Backend LLM cost figures (`total_cost_usd` etc.) are INTERNAL telemetry — never show them to the customer, in this summary or any progress line.

read each row from one envelope:

- `scenario_set_id` ← `id`
- `dataset_name` ← `detail.dataset_name`
- `status` ← `status` (`queued | running | done | failed`)
- `count` ← `detail.scenarios_completed` / `detail.scenarios_total`
- `started_at` ← `started_at`

```
| scenario_set_id (short) | dataset_name      | status | count | started_at        |
|-------------------------|-------------------|--------|-------|-------------------|
| 6c754f58…               | dataset_a         | done   | 3/3   | YYYY-MM-DD HH:MM  |
| 7a8b9012…               | dataset_b         | done   | 5/5   | YYYY-MM-DD HH:MM  |
| 89cde456…               | dataset_c         | failed | 1/3   | YYYY-MM-DD HH:MM  |
```

Pull a `plurai_sim/.scenario_set_id` from the cwd (if present) and mark
the matching row with `*` so the user sees which set their current
plurai_sim/ points at.

### Mode B — detail (scenario_set_id arg)

When invoked with `scenario_set_id`, call
`get_artifact_meta(scenario_set_id)` and render per-scenario rows. The
tool returns a **Job envelope**; read the header from `id` / `status` / `detail.dataset_name`, the coverage from
`detail.dataset_metadata` / `detail.coverage`, and the per-scenario rows from
`detail.scenarios` (each `{name, complexity_level, subtlety_level,
target_flows, current_elements}`):

```
Set: 6c754f58-…
  dataset_name: generated_dataset
  status:       done

Coverage:
  search_flow:        3 ⬤⬤⬤
  bulk_update_flow:   1 ⬤
  ...

Scenarios:
  | name                                 | complexity | subtlety | target_flows                       | current_elements                       |
  |--------------------------------------|------------|----------|------------------------------------|----------------------------------------|
  | scenario_01                          | 3          | 3.5      | search, create, update             | ambiguous_request, revert_…            |
  | scenario_02                          | 2          | 4.5      | search, undo, bulk_update          | stale_in_memory_state                  |
  | scenario_03                          | 3          | 2.5      | update, create, search             | invalid_input, budget_exhausted        |
```

If the user wants to look at one scenario's full content (the actual
scenario.yaml prose, initial_world_state.yaml, etc.), call
`get_scenario(scenario_set_id, scenario_name)` and dump the files
inline — don't write them to disk. When explaining the files: `seed.txt`
is the AUTHORING INPUT (the dimension-graph seed the writing session
started from, persisted for chain inspection) — the authored scenario
legitimately evolves past it, so a premise difference between seed.txt
and scenario.yaml is the pipeline working, not drift or a defect.

### Mode C — delete (scenario_set_id arg + `--delete` flag)

When invoked as `/list-scenarios --delete <scenario_set_id>`, confirm
with the user FIRST (this destroys GT), then call
`delete_artifact(scenario_set_id)`. Inside a driving command's flow window
that confirmation is a sanctioned ask: first run
`bash "${CLAUDE_PLUGIN_ROOT}/scripts/flow-window.sh" sanction delete-confirm`,
or it is denied — and a denial is not a stop, so the delete would run unconfirmed. It returns a generic deletion
result `{id: <uuid>, deleted: <bool>}` (`deleted=false` means the set was
already gone — idempotent). On `deleted=true`, print:

```
Deleted scenario_set_id=<uuid>.
```

If the customer's `plurai_sim/.scenario_set_id` pointed at the deleted
set, also `rm` that file so a subsequent `/simulation-run`
fails fast rather than running against a missing set.

## Hard rules

- **Read-only by default.** Modes A and B never mutate the backend.
- **Mode C requires explicit confirmation.** Do not delete without
  asking the user, even when `--delete` is passed.
- **Don't materialize scenarios to disk in any mode.** The backend is
  canonical; inspection is in-chat only. The one sanctioned mutation is the
  backend-gated `edit_scenario_gt` tool (grading-GT fields only —
  the `edit-scenarios` skill); there is still no local-file path.

## Glossary

- **scenario set** — one batch of backend-generated scenarios stored
  on the backend, identified by `scenario_set_id`.
- **coverage** — how many times each dimension-graph flow was the
  target of a walk in this batch. `0` means the batch left that flow
  uncovered.
