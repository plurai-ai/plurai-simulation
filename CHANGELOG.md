# Changelog

## [1.1.0]

- The plugin installs SDK 1.1.0, which adds `plurai ci run` and `plurai ci validate` for running your simulations in CI.
- A project's lock decides which SDK it runs. The plugin accepts the SDK it was tested with and every later release of the same minor (`1.0.3` and `1.0.9` with a `1.0.3` pin); an older release is offered the install, and another minor is refused with a stop and no question. Pre-releases order below their release, so a dev build or release candidate pin admits its own later builds and the release.
- In a uv project (`uv.lock` and a `pyproject.toml`), the plugin adds the SDK with `uv add --dev` and the marker `python_version >= "3.12"`, after one question that names `pyproject.toml` and `uv.lock` and says other packages in the lock can change. The marker keeps a project whose `requires-python` reaches below 3.12 resolvable. A workspace member adds to its own `pyproject.toml` and the lock above it. A Poetry project (`poetry.lock` and a `pyproject.toml`) gets the same question, naming `pyproject.toml` and `poetry.lock`, and then `poetry --no-plugins add --group dev` with the same marker (where `poetry` is not on PATH, Poetry runs through `uvx` at one fixed release from `pypi.org` with uv's configuration off, so the repository's own settings never choose the tool; that release is current, so a lock written by a recent Poetry is read as fresh and the add leaves its format alone; the project's own Poetry sources still apply to the SDK); when it fails, for instance on a version conflict with the agent's own packages, both files are put back, and the text names Poetry's reason. A requirements project gets the question too, naming the requirements files that list the SDK; after a yes the release is installed into the project's environment and the `plurai-simulation-sdk` line of those files is set to it, keeping extras, marker and comment. A line is never added to a file that did not list the SDK, and a file is put back when the install fails. A project the plugin cannot write (no `pyproject.toml` beside `poetry.lock`, neither `poetry` nor `uvx`, a requirements file with hashes) is told the line and nothing runs; `resolve_plurai.py --install-line` exits 6 for a Poetry or requirements project, the fallback when no environment or no SDK that can run is found. A run nobody answers prints the stop text in every kind of project.
- An SDK older than the plugin's release that also lacks a command the skill needs (the first `/simulation-ci` run on `1.0.x`, which has no `ci` commands) gets the update question, or the install on a yes, in every kind of project, instead of the stop that says the SDK is too old. An SDK at the release or later that lacks a command keeps that stop, and a run nobody answers prints the stop text with the install line.
- Each `evals[]` row of a run's `run.json` carries the effective tier the backend serves for the eval set (`get_artifact_meta` → `detail.policy_tiers`), with `tier_source: backend`. `/simulation-run` saves that answer as `eval_set_meta.json` in the run folder before it builds `run.json`, and the build reads only an answer for the eval set it was given (`--eval-set-id`). The plugin derives no tier from `policies_config.yaml`: without the answer every row's tier is `unknown`, the build says so, and `red_cells.py list` names stakes policies by severity alone.
- `/simulation-ci` sets up CI for your simulations in one command, and edits that setup when you run it again.
  - **Setup.** It finds each `plurai_sim/` directory and asks which get CI, runs the CI readiness check (every finding comes with its fix), proposes a smoke list for you to confirm, renders one workflow file per agent (`.github/workflows/plurai-<agent>.yml`) and a `plurai_sim/ci.yaml` from templates by script, and runs `plurai ci validate`. It asks no trigger question, no `anonymize` question and no live-tools question. A config that does not declare `anonymize` reads as `false` in CI (a CI run never reads the key), so the readiness check raises no finding for it and the `posture` line says "raw". Tool modes stay as configured, and `agent-env-missing` lists the names those tools read.
  - **Printed lines.** It prints `plurai login`, `plurai ci token --github <owner>/<repo>`, one `gh secret set <NAME>` per `agent.env` name, how to start a manual run (the Actions tab "Run workflow" button, or `gh workflow run plurai-<agent>.yml --ref <branch> -f selection=smoke`; the workflow file must be on the default branch first) and a local `plurai ci run` rehearsal. It never runs them and never sees a value. Until the secrets are set, a run is not measured and its heading says why: `not measured: <NAME> empty` or `not measured: no secrets (PLURAI_TOKEN is not set)`.
  - **Triggers.** The workflow starts by hand, because each run spends credits: `workflow_dispatch` with a `selection` choice input (`smoke` or `full`, default `smoke`). The other four events (`pull_request`, `merge_group`, `push` and a nightly `schedule`) are commented lines with a one-line note each, naming the suite it runs and that each run spends credits; the schedule note adds that GitHub turns a schedule off in a public repository after 60 days without activity and notifies whoever last edited the cron line. The user removes the `# ` of the lines they want. The triggers are a user-owned block that a re-render keeps as the file holds it, and `ci_render.py check` flags `pull_request_target` in it (the action refuses it with exit 65). A dispatch concurrency group names its ref, so manual runs on two branches never share one. The check "Plurai simulation (<agent>)" can be required in branch protection once `pull_request` is on; a required check that never runs on a pull request blocks every merge. The workflow runs against Plurai's production backend and sets no url. Write access to the repository is the boundary, and a team that wants a gate adds a GitHub Environment with required reviewers.
  - **Main's baseline.** Main never runs on its own. The setup summary, the CI readiness check's warning and a comment in the triggers block say that after a suite change merges, the workflow should run on the default branch (Actions > Run workflow) or `push` should be on, so the next pull request has a "vs main" comparison.
  - **Workflow.** Two jobs: `simulate` (read-only; runs the agent) and `report` (the only write permission; never runs agent code). On every event that ran `simulate`, `report` creates a check run, "Plurai simulation results (<agent>)", that holds the report (the counts line as its title, the verdict as its conclusion), through the Checks API with the job's token and no third-party action. On pull requests it also posts the one sticky comment. It needs `pull-requests: write` and `checks: write` and runs on `always()`; deleting the job turns both off. A fork or Dependabot pull request, whose token cannot write, gets a note in the job summary.
  - **Managed block and user-owned regions.** A re-render regenerates the managed block and keeps the triggers, the wall bound (`timeout-minutes` only), the install steps, the `env:` block and the cloud-credentials step as the file holds them. A managed block edited by hand is not overwritten: `render` prints `REFUSED-DRIFT` with the diff, writes nothing and exits 1 unless `--force`; a block of an older revision is upgraded without `--force`. `ci_render.py check` reports `DRIFT`, `ENV-MISSING`, `NOT-MANAGED`, `FORBIDDEN-TRIGGER` and `FORBIDDEN-WALL-BOUND`. A confirmed `--smoke` list is written into an existing `ci.yaml` through the same line editor as `ci_edit.py smoke` (`SMOKE-SET`), comments kept.
  - **Install step.** It builds the environment the action runs the agent in: the nearest `.venv` above `workdir`, else `$VIRTUAL_ENV`, else `python3`. A Poetry project gets `poetry install --no-root --with dev` with `POETRY_VIRTUALENVS_IN_PROJECT: "true"`, a uv project `uv sync --no-default-groups --group dev`; the group flag is written only when `pyproject.toml` defines the dev group. The dev group holds the SDK the plugin adds, so CI runs the SDK the lock names, and an SDK bump inside the minor (a Dependabot or Renovate PR) needs no new action release. `--no-dev` or `--without dev` in the install step leaves the SDK out. A requirements project runs `pip install -r` into the interpreter `setup-python` puts on `PATH`.
  - **CI readiness check.** The check compares the minor of the SDK a lock or venv holds with the minor of the plugin's own pin and reads no network. It reads each suite id from the copies CI reads, in `read_id.py` order (the env folder's marker, its manifest key, the root marker), needs only one of them, and raises `id-copies-disagree` when they hold different ids, naming each file with its id and the id CI reads; the fix asks which id the suite should test and writes it into every copy with `write_id_file.py set --kind scenarios|evals <id> --workdir <plurai_sim>/envs/<env>`. `id-conflict` reports an id file that holds a merge conflict. `id-files-uncommitted` is an `ADVISE`, never a block: a suite id file differs from `HEAD`. `trials-too-low` flags a `ci.yaml` with `trials` below 2. `plurai ci validate` runs last, once no other finding needs a fix.
  - **Smoke size.** The proposal keeps a smoke run (the smoke list and every `regression_*` scenario, times `trials`) to 12 threads. That is a provisional default, not a limit: a longer list or more trials is applied, and the render and `ci_edit.py smoke` / `trials` print a `NOTE` that the run costs more threads; the CI readiness check says the same as an `ADVISE` (`smoke-over-default`).
  - **Reserved `agent.env` names.** A CI run refuses the names that carry a CI credential, a token endpoint or a file that steers the job (`GITHUB_TOKEN`, `GH_TOKEN`, `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, `GITHUB_ENV`, `CI_JOB_TOKEN`, `SYSTEM_ACCESSTOKEN` and others), every `PLURAI_*` name, and any name under a CI platform prefix that reads as a credential (`CI_DEPLOY_KEY`, `CIRCLE_TOKEN`), in any case. The plugin applies the SDK's rule name for name and refuses each where it is declared, with the variable and the reason, never dropping it: a `FIX` in the CI readiness check (`agent-env-reserved`), and a refusal from `ci_render.py render` / `check` / `lines` and `ci_edit.py agent-env add` / `github-names`. A platform's other variables (`CI_ENVIRONMENT`, `GITHUB_REPOSITORY`, `RUNNER_TEMP`) are ordinary names.
  - **Run again.** On a configured repository the CI readiness check runs first: `ci_edit.py state` carries each agent's `FIX` lines (`fixes`), the workflow's `events` and whether `pull_request` is on, and a repository where some agents are configured and others are not gets the configured agents' fixes before the first setup. The Dependabot secrets offer says it is useful only once `pull_request` is uncommented, while it is commented out. The edits keep the user's comments and run `plurai ci validate`: the smoke list, `trials` (at least 2), `fail_on.tags`, overrides (once a report exists), `agent.env` names, Dependabot secrets, adding or removing an agent, and a managed-block re-render. `ci_edit.py smoke` refuses an empty list. `ci_edit.py pending` lists the files to commit from `git status --porcelain` under each `plurai_sim/` and in `.github/workflows/plurai-*.yml` (a workflow of the user's own is never listed); the skill names them from that list after each edit and before a commit.
- `/edit-evals` says how to change a policy's `verdict_tier`: through the edit session, never as a `ci.yaml` override.
- CI reads a scenario or eval set id from the env folder `ci.yaml` names (`envs/<env>/`), where the edit skills write it when an env is active. The writer keeps the root copy in step: a write of `.scenario_set_id` or `.eval_set_id` in that env folder (or in any saved env while there is no `ci.yaml`) also writes `plurai_sim/.scenario_set_id` or `.eval_set_id`, and so does switching to that env.
- Every skill and script reads a committed scenario, eval set or env id through `scripts/read_id.py`, which takes the copies in the order CI reads them: the active env folder's marker, its manifest key, then the root marker (the root only when it copies that env). An edit on a saved env with no marker in its folder (a layout `/save-env` made) reads that env's id. In `plurai_sim/` without an active env (a fresh clone), the reader and `write_id_file.py` use the env folder `ci.yaml` names, so an edit there moves every copy. `/save-env` writes the env folder's markers next to its manifest. Every skill runs `write_id_file.py` under `$PLURAI_PY`, which reads a saved env's manifest, and the edit skills say never to write an id file another way. `stage-inputs.sh` stages the manifest and the root marker a suite id write moved with the env folder's marker. `resolve-python.sh` finds the project's `.venv` above the working directory, up to the project root, so a snippet run from `plurai_sim/` finds PyYAML. `/list-scenarios` leaves the id file of a deleted set alone and tells the user.
- `scripts/id_changes.py` lists, from git, the suite id files (markers and manifest id keys) that differ from `HEAD`, and, with a snapshot, the ones a step changed. Every edit skill (`/edit-evals`, `/edit-scenarios`, `/edit-env`) ends by listing them and telling the user to commit them with the change; `/simulation-run` says plainly, with both ids, when a run moved an id file and that committing it changes what CI runs. The `/simulation-ci` CI readiness check warns (`id-files-uncommitted`, an `ADVISE`, never a block) on an id file that differs from `HEAD`.
- `read_id.py` (and `committed_id`, by raising `ConflictError`) stops on an id file that holds git conflict markers and says to resolve the merge conflict, take main's id and re-apply the edit with the skill that made it.
- `/edit-scenarios` states the two supported ways to remove one scenario, since the backend has no tool for it: ignore it in CI with an override, or leave it out of a regenerated set and relink the evals.
- A `/simulation-run` report ends with a `## CI verdict` block: the verdict `plurai ci run` gives the same `run.json` (failed, unstable, advisory, passed, not applicable or not measured for each scenario × policy, the heading that counts them, and the exit code a CI run would give), drawn by the SDK's `plurai.report`. `scripts/ci_verdict.py` adds it to `analytics.md`; nothing else in the report changes. The block leaves out what `ci.yaml` adds in CI (overrides, the infra retry, the quarantine cap). When the installed SDK has no `plurai.report`, or the run drew one sample and has no `trials` block, the block is the single line `CI verdict: not available.` with the reason.
- One script writes the id files. `scripts/write_id_file.py` takes the backend's answer and writes the one id file that moved (`.scenario_set_id`, `.eval_set_id`, `.env_id`, `.corpus_id`, `.corpus_ids`, the env manifest's key beside it). An edit of a scenario set, eval set, env or corpus ships under a new id, answered as `minted_id`; that is the only id written. The `target_id` of an open edit session is a draft copy and `source_id` the original, and neither is ever written. An answer with `minted_id: null` (nothing shipped) writes nothing, and an answer with no `minted_id` field is refused. A scenario edit moves `.scenario_set_id` only, and a relink, an eval edit or an optimizer adopt or revert moves `.eval_set_id` only.
- Every skill that changes an id calls the writer instead of writing the file from its own instructions: `/generate-scenarios`, `/refine-scenarios`, `/generate-evals`, `/generate-mock-env`, `/upload-scenario-bundle`, `/trace-to-scenarios`, `/upload-doc-examples`, `/manage-envs` (save and switch), `/simulation-generate-suite`, the re-plant of `/simulation-run`, and the edit skills `/edit-scenarios`, `/edit-evals`, `/optimize-eval` and `/edit-env` (an env or a corpus edit). A corpus edit names the corpus id it replaces, and the writer swaps it in every corpus marker that holds it.
- `/record-regression` plants the regression into the scenario set when a fix is accepted. It stages the one recorded folder, uploads it as a bundle, tops the current scenario set up with it (`bundle_only=true` with `count` = the donor's scenario count: the backend adopts every donor scenario, authors the folder alone and walks nothing) into a new scenario set id, and writes the top-up's `detail.minted_id` with the writer (`write_id_file.py created --kind scenarios --top-up`), so the id belongs in the same commit as the fix. The eval set id does not move, and `--verify` still checks the fix through the original scenario. At a suite build's gate exit nothing is planted: the final batch carries the folder. `final_bundle.py stage --only <folder>` stages named regressions alone.
- The skills state the top-up count rules as the backend applies them. A top-up needs `count` above the number of adoptable scenarios, with or without `additional_bundle_id`; `bundle_only` is the one exception, and only `/record-regression` passes it (it needs `adopt_from_scenario_set_id` and `additional_bundle_id`, refuses unless every donor scenario is adoptable and `count` equals that number, and stops with the numbers on a refusal). The cap counts the scenarios the job generates plus the folders, not the adopted ones, so `/record-regression` stages with `--count 0` and a suite at the cap can still record a regression. `/generate-scenarios` no longer says the additional bundle excludes `adopt_from_scenario_set_id`.
- `suite.json` is no longer committed. The managed `.gitignore` block (rev 12) stops allowing it, and `stage-inputs.sh` stops staging it. `scenarios.md` and `evals.md` stay local reading copies; no skill checks or refreshes them against the ids. After a scan the block is replaced at the new rev.
- An applied `edit_scenario_gt` or an optimizer adopt no longer leaves the id unchanged: the skills tell the model to use the new id for the next call and for the re-score.

- The scan records the production hosts before its own verify step.
- A red result restored after the audit list was cut is audited once and never holds the scores.
- An agent that gives up on its own fault before the scenario's goal came up is scored as missing the goal.
- The report page shows the production turns a trace scenario resumes from.
- Each regression in `run.json` now lists, beside its result, the other evals that failed the issue's turn when it was recorded or failed on these replays: whether each failed when recorded, how many replays it failed and measured, and whether it came from a production trace; every `evals[]` row also carries `from_trace`.

## [1.0.0]

First public release of the Plurai simulation plugin. It sets up Plurai simulation for an AI agent: it reads the agent's code, writes a `simulate.py` that stubs the agent's production dependencies and routes its tool calls to mocks, builds a mocked world, scenarios and evals, runs the suite against the Plurai backend, and writes an evidence-backed fix plan. It does not modify the agent's source.

- Install from the public `plurai-plugins` marketplace: `/plugin marketplace add plurai-ai/plurai-plugins`, then `/plugin install plurai-simulation@plurai-plugins`. The README is the quickstart.
- The first Plurai command signs you in. With no login saved, it installs the SDK when it is missing (it asks first) and runs the SDK's `plurai login`, which opens the browser; the key is saved by the SDK and never shown, typed or copied. A machine without a browser signs in as `docs/sign-in-without-a-browser.md` describes. A Claude Code session that started before the first login asks once to run `/mcp reconnect all`, then carries on by itself.
- `/simulate <agent module>` runs the whole flow. Each stage is also a command of its own: `/simulation-scan-agent`, `/analyze-traces` (optional, grounds the suite in real production traces), `/simulation-generate-suite`, `/simulation-run` and `/simulation-fixes`. Further commands refine scenarios, edit a mock environment, build a knowledge corpus, upload document examples or scenario bundles, record a regression, and diagnose or uninstall the plugin.
- A finished run ends on one message with its outcome, the number of agent issues with a link to the fix plan, the overview page link, and the choices the run took on a default. The overview page opens in your browser when the run starts and updates live; it shows the agent map, each eval's kind and what it checks, each scenario's card and every conversation's verdicts. The page stays in place after the run ends, so the open tab still refreshes.
- Claude Code is supported. Codex CLI and Copilot CLI are beta. macOS and Linux are supported. Windows (PowerShell, with Git for Windows; see `docs/install-windows.md`) is supported for Python agents; agents that need the Node bridge are not supported on Windows. On a hosted Agentforce agent, `/simulate` asks once at the start whether it may use your org.
- The plugin installs the one release of the `plurai-simulation-sdk` package it was tested with, into the project's environment. The SDK needs Python 3.12 or newer; the plugin's own hooks and scripts need a `python3` on the PATH. An agent written in Node also needs Node 22.15 or newer, on macOS or Linux.
- Data leaves your machine only through the SDK's `plurai ingest-*` commands and the backend calls of the flows. You approve each command before it runs, the SDK prints a disclosure preview of each upload, and an append-only audit log at `.plurai/uploads/audit.log` records what was sent and under which anonymization posture. The plugin sends no telemetry.
- The files the plugin generates in your repository belong to you. `docs/what-the-plugin-writes.md` lists every file and folder the plugin writes, and `/plurai-uninstall` removes them after you confirm.
- A newer plugin release is announced once a day, from the public plugin repository's tag list, and never blocks; `PLURAI_NO_UPDATE_NOTICE=1` turns the read off. A plugin or SDK version that Plurai refuses reads one short text with the update command for your harness, on Claude Code, Codex CLI and Copilot CLI alike. An SDK older than the one the plugin installs is offered the install once: "This plugin release needs plurai-simulation-sdk 1.0.0; this project has the older 1.0.0rc1. Install 1.0.0 into .venv now? It may change other packages there, and Plurai commands wait until it is done." (the versions and the environment are your own).
- A stop that is a matter for Plurai reads one of three fixed texts, the same in all three harnesses and in the SDK. When something on Plurai's side needs a closer look: "We hit an issue that needs a closer look from the Plurai team. Reach out at support@plurai.ai or on Discord: https://discord.gg/bg34gh76uJ and we'll dig into it." When the provider is out of room: "Plurai is in high demand right now and we couldn't fit your run in. Please try again in about 20 minutes." When Plurai cannot be reached or says it is unavailable, a third text says so and asks you to try again shortly. A credit stop names what to do to continue and the command that continues it. A stop is said once, as the last message of the turn, and halts the run until you type a message.
- A run with nobody at the keyboard ends with exit 5 and the stop text in its log when Plurai stops it, and as a failure with the refusal text when Plurai refuses its version; neither is retried until a time limit.
- On Claude Code, when your organization's settings keep the plugin's hooks from running, the flows run in a limited mode and say once, in plain words, that some automatic checks are off and how to turn them back on.
